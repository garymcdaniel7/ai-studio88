# AI Studio — UAT Audit Report
**Date:** 2026-08-23 · **Auditor:** Hermes (acting as UAT test team) · **Surface:** localhost:3000 + :8000

Scope: I booted the backend (FastAPI) and frontend (Next.js), swept all 24 routes as an anonymous user, attempted signup as a new user, and reconciled the running UI against the code. Every finding below was reproduced, not guessed.

---

## Executive Summary

The platform has a **polished, well-gated shell and zero monetization**. Auth-gating and the landing page are genuinely strong. But the app cannot reach its own data layer in a fresh checkout, several core routers silently fail to load, and — most importantly for the stated goal ("profit that frees Gary") — **there is no way for any user to pay for anything.**

## 🔴 Critical Findings

### C1. The app has NO monetization path — Stripe is dead config
**Location:** `backend/app/core/config.py:294-296` (env vars only); no `stripe` import, no checkout, no billing endpoint, no webhook anywhere in `backend/app` or `frontend/src`.
**Evidence:** Landing page promises "$0/month + pay only for GPU time." Stripe env vars exist. But grepping all app code (excluding `.venv`) for `import stripe`, `checkout`, `billing`, `subscribe` returns **nothing**.
**Impact:** Users connect their *own* Vast.ai/RunPod account and pay the GPU provider directly. AI Studio collects $0 from anyone, for anything. This is the single biggest blocker to the core business goal — the product currently cannot earn a dollar.

### C2. The database layer is permanently broken in a fresh checkout
**Location:** repo-root `supabase/` data directory shadows the PyPI `supabase` package.
**Evidence:** `/ready` → `database: unavailable — cannot import name 'create_client' from 'supabase' (unknown location)`. Running `python -c "import supabase"` shows `supabase.__file__ = None` because Python resolves the namespace to the local `supabase/` folder (which has no `__init__.py`). This happens precisely when run from repo root — exactly how `start.sh` runs it.
**Impact:** Projects, talent, generation history, publishing posts — everything DB-backed — cannot load in local dev. Authenticated flows would render empty/error states.

## 🟠 High Findings

### H1. requirements.txt omits `pyjwt` and `passlib`, silently killing 9 routers
**Evidence:** Backend startup logs `UserWarning: v1 router not loaded: No module named 'jwt'` (×7) and `... 'passlib'` (×2). Neither `pyjwt` nor `passlib` is in `requirements.txt`, yet the code imports both. The app "starts" (liveness 200) while core routers are absent. After I installed them, routers load (`All routers loaded successfully`).

### H2. Fresh-onboarding boot is broken (venv under-provisioned + `uv` conflict)
**Evidence:**
- `start.sh` uses `uv run uvicorn ...` which fails: `No solution found ... gotrue==2.9.0 depends on httpx[http2]>=0.24,<0.28 and your project depends on httpx==0.28.1`.
- The existing venv lacks `uvicorn`, `requests`, `boto3`, `python-multipart` even though several are in `requirements.txt`. I had to install 5 packages to get the backend to run.
- **Net:** a new contributor following README/start.sh cannot boot the app.

## 🟡 Medium Findings

### M1. "Skip login (dev mode only)" is a no-op
**Evidence:** Button (`login/page.tsx:284`) just does `router.push(redirect)` without establishing any session. After clicking, navigation to any protected route bounces straight back to `/login`. It neither logs in nor stays — confusing in dev, harmless in prod (gated by `NODE_ENV`).

### M2. Signup friction: email confirmation + raw 429
**Evidence:** Signup returns "Account created! Check your email to confirm" (confirmation required, no instant access). Three rapid attempts then hit Supabase `429 email rate limit exceeded`, surfaced verbatim as a raw error string with no retry guidance or countdown.

### M3. Over-strict email validation
**Evidence:** `uat.tester.1787450351993@example.com` (valid RFC 5321) rejected as "Email address ... is invalid". Likely a dots/format rule — can silently turn away real users (e.g. `first.last+tag@domain`).

### M4. Core creation is a single 1,822-line wall of controls
**Evidence:** `create/page.tsx` exposes ~60 parameters in one page — model, LoRA, control-net, negative prompt, steps/CFG/seed/width/height, presets, batch count, voice provider, music mood, video duration/FPS — behind only an "Advanced" disclosure toggle. The audience is creatives, not ML engineers; this is heavy cognitive load with no guided or progressive flow.

## 🔵 Low Findings

### L1. Generation runs in simulation mode by default
`/ready` → `generation: degraded — Running in simulation mode`. Fine for dev, but a new user could generate "successful" results that never hit a real GPU.

### L2. Publish flow depends on a router that was down until I fixed deps
`publish/page.tsx` POSTs to `/api/v1/publishing/posts`, which lived under the api_v1 router that failed on missing `jwt`. Publishing was entirely unavailable before provisioning.

### L3. No middleware file; auth is client-side only
`frontend/src` has no `middleware.ts`. Auth is enforced via `ProtectedRoute` client component (Supabase session). Works in the sweep, but relies on client JS; a server-side middleware layer would be more robust.

## ✅ Working Well

1. **Auth gating** — all 24 protected routes redirect cleanly to `login?redirect=...`; zero console errors, zero failed requests in the anonymous sweep. Role hierarchy + capability gates (`CapabilityGate`, `ProtectedRoute`, governed dialogs) are well-built.
2. **Landing page** — strong, revenue-conscious marketing copy (pay-as-you-go, no lock-in, competitor table, real cost examples). A solid conversion foundation.
3. **Infra integrations configured** — `/ready` reports storage (B2), GPU (Vast), auth, LLM (Ollama) as **ready** with live credentials.
4. **Cost transparency signal** — create result carries `estimated_cost`; `admin/fleet` shows "Pause (stop billing)" with consequence dialogs. The instinct to show users money is present.

## 🧍 Human-Centric UX Recommendations (design thinking)

**1. Progressive disclosure, not a control wall.** Group the create flow into stages — **Prompt → Choose style → Generate** — with advanced settings tucked behind one collapsible panel. Show the **1–3 parameters that matter** to a creator (quality/speed, aspect ratio, count) and hide steps/CFG/seed unless the user opts into "Expert mode." For your creator personas, offer **preset modes** ("Quick", "Pro", "Custom").

**2. Guided empty states.** Every module (Talent, Projects, Publish) should meet a new user with a one-sentence "what this is + one-click first action," not an empty table. The onboarding persona pick is a good start — extend it to produce a **personalized first-actions checklist**.

**3. Inline cost preview before action.** You already compute `estimated_cost`; surface it **before** the user hits Generate (and before launching a worker), not after. "This image ≈ $0.005 · 4 left at your pace" builds trust and reduces bill-shock.

**4. Plain-language microcopy.** Replace ML jargon ("LoRA strength", "CFG", "steps", "control-net") with benefit phrasing and hover tooltips. Creatives shouldn't need a glossary.

**5. Fix the on-ramp honesty.** A new user cannot actually get in (email confirm) and the dev skip is broken. Decide the intended onboarding and make it actually work end-to-end — silent no-op CTAs erode trust immediately.

**6. Autosave + recovery.** Long creative sessions lose state on refresh (favorites are localStorage only). Persist drafts/prompt history server-side so creators never lose a prompt mid-flow (ADHD-friendly, matches your own working style).

## 💰 Revenue Generation Recommendations (grounded in what exists)

**1. Actually implement billing — pick a model.** You have Stripe env vars and zero code. Given "no subscription, pay for GPU time," the natural implementation is **Stripe usage-based / metered billing** on top of your own cost ledger (`cost_ledger.py` exists!). Charge a **small platform margin on compute** (e.g. you orchestrate the Vast/RunPod worker and bill the creator through Stripe instead of them paying the provider directly). That margin is your revenue and it maps 1:1 to the "pay only for GPU time" promise already on the landing page.

**2. Add a "Pro creator" tier** for the super-users your landing page already names (500+ images/mo): higher concurrency, priority GPU queue, batch/API access, team seats. Reuses the role hierarchy you've built.

**3. LoRA/identity is your moat — package it.** "Train custom AI talent from 10–50 photos" is your differentiator. Sell **trained-talent packages / template LoRAs** and a **talent licensing marketplace** — creators pay per use of a premium identity. This is where AI-influencer content genuinely monetizes, and it's not a commodity like image generation.

**4. Publish is a retention + upsell surface.** You already integrate Instagram/TikTok/YouTube. Bundle a **scheduling/distribution tier** (per-platform posting limits free, unlimited paid) and add **cross-platform analytics** so the value visibly compounds — churn killer.

**5. Meter the free tier to prove value, then convert.** Gate the heavy stuff (video, LoRA training) behind the metered/paid path; keep image generation as the irresistible free sample. Your own "free vs Pro" framing on the landing page can be delivered with a real gate.
